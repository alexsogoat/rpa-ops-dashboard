# 성능 측정과 개선 계획

> 2026-11-04에 v1.0.0을 측정한 기준선이다. 개선 PR마다 같은 방법으로 다시 재서 전·후 수치를 PR 설명과 이 문서에 남긴다.

## 측정 방법

- 대상: `npm run build` 결과물을 Vercel처럼 brotli 압축 + SPA rewrites로 서빙 (로컬)
- 도구: Playwright(Chromium). 첫 방문(캐시·서비스 워커 없음)을 3회 재서 중앙값을 쓴다
- 조건
  - 데스크톱 회선: RTT 40ms · 10Mbps
  - 모바일 수준: RTT 150ms · 1.6Mbps · CPU 4배 느림 (Lighthouse 모바일 기본 조건과 비슷)
- 지표
  - 첫 화면(FCP): 처음으로 글자가 그려진 시각
  - 데이터 표시: 요약 카드와 프로세스 목록 표가 모두 보인 시각
- 직접 재볼 때: Chrome DevTools의 Lighthouse(모바일, 시크릿 창)나 Performance 패널(Network "Slow 4G" + CPU 4x). 도구마다 절대값이 다르므로 같은 도구로 전·후를 비교한다

## 기준선 (v1.0.0)

| 조건 | 첫 화면 | 데이터 표시 |
|---|---|---|
| 데스크톱 회선 | 0.34초 | 0.36초 |
| 모바일 수준 | 1.48초 | 1.63초 |

모바일 수준에서 1.63초가 걸리는 과정:

| 구간 | 끝나는 시각 | 걸린 시간 |
|---|---|---|
| HTML · JS 다운로드 | 1.05초 | 1.05초 |
| JS 실행 (모든 모듈 평가) | 1.25초 | 0.19초 |
| MSW 워커 등록 (`worker.start()`) | 1.33초 | 0.09초 |
| 첫 렌더링 → API 요청 시작 | 1.48초 | 0.14초 |
| API 응답(MSW) → 화면 표시 | 1.63초 | 0.16초 |

`#root`가 비어 있고 React는 워커 준비 뒤에 렌더링하므로, **처음 1.48초 동안 화면이 비어 있다.**

### 번들 구성

JS 파일 1개, 698 KB (gzip 246 KB · brotli 145 KB). 비율은 소스맵으로 집계했다.

| 구성 | 크기 | 비율 |
|---|---|---|
| MSW와 의존성 + 목 데이터·핸들러 | 409 KB | 61% |
| └ 그중 tldts (공개 접미사 목록. MSW 쿠키 처리용 tough-cookie가 사용) | 246 KB | 37% |
| react-dom · react · scheduler | 214 KB | 32% |
| react-router | 36 KB | 5% |
| 앱 코드 (`src`, 목 제외) | 13 KB | 2% |

- 번들의 61%가 배포 환경에서도 켜는 MSW다. 첫 API 요청 전에 반드시 받아야 하므로, 지금 구조에서는 첫 로딩 경로에서 뺄 수 없다
- 앱 코드는 2%뿐이라 화면 단위 코드 분할(`React.lazy`)은 효과가 거의 없다

### 화면 이동

목록 → 상세 → 목록으로 돌아오면 요약·목록 API를 다시 요청하고 "불러오는 중"이 잠깐 보인다. 지금은 MSW 응답이 25ms 안팎이라 깜빡이는 정도지만, 실서버라면 돌아올 때마다 왕복 시간만큼 빈 영역이 생긴다. 필터·검색어도 초기화된다(컴포넌트 상태라서).

## 적용 결과 (perf 1차: 1~3번)

같은 측정 방법으로 수정 전·후를 연달아 쟀다 (3회 중앙값). 재방문은 같은 브라우저로 다시 연 경우이고, 서버가 ETag 재검증에 304로 답하도록 했다.

| 시나리오 | 수정 전 | 수정 후 |
|---|---|---|
| 첫 방문 · 데스크톱 (첫 화면 / 데이터) | 0.36 / 0.38초 | **0.14** / 0.35초 |
| 첫 방문 · 모바일 (첫 화면 / 데이터) | 1.53 / 1.66초 | **0.44** / 1.70초 |
| 재방문 · 데스크톱 (첫 화면 / 데이터) | 0.16 / 0.16초 | **0.07 / 0.11초** |
| 재방문 · 모바일 (첫 화면 / 데이터) | 0.49 / 0.57초 | **0.20 / 0.40초** |
| 재방문 때 `/assets` 파일의 네트워크 왕복 | 2개 (304 재검증) | **0개** (브라우저 캐시) |
| 목록 복귀 · 상세 재방문 | 로딩 문구 보임, 약 30ms | **로딩 문구 없음**, 10ms 안팎 |
| 목록 복귀 · 상세 재방문 (API 응답 300ms 가정) | 로딩 문구 보임, 0.33초 | **로딩 문구 없음**, 0.01초 |

- 첫 방문의 데이터 표시 시각은 그대로다 (차이는 측정 오차 범위). 1번은 빈 화면을 없앨 뿐이고, 데이터 표시를 앞당기는 것은 4번(MSW 제거)의 몫이다
- 재방문의 "수정 전"은 Vercel 기본 헤더를 `public, max-age=0, must-revalidate`(ETag 재검증)로 가정한 값이다. 배포 사이트의 실제 헤더는 이 측정 환경에서 확인하지 못했다. 이미 장기 캐시였다면 3번의 효과는 없고, 재방문 개선분은 1번(첫 화면)만 남는다
- 2번은 화면 이동에만 효과가 있다. 캐시가 메모리에 있어 새로고침하면 비워진다
- "API 응답 300ms 가정"은 측정용 복사본에서만 MSW 응답을 300ms 늦춰 실서버 왕복을 흉내 낸 값이다

### 1. 정적 뼈대 — 적용

- `index.html`의 `<div id="root">` 안에 상단 바와 "불러오는 중…"을 HTML로 넣었다. CSS는 `<head>`에서 먼저 받으므로 JS를 기다리지 않고 그려지고, React가 첫 렌더링 때 `#root` 안을 통째로 바꾼다
- 상단 바 마크업은 `App.tsx`와 같게 맞추고, 두 곳을 함께 고쳐야 한다는 주석을 양쪽에 남겼다. 다르면 렌더링 순간 화면이 움직인다
- C# 비유: 무거운 초기화 전에 스플래시 화면을 먼저 띄우는 WinForms 앱

### 2. 조회 캐시 — 적용

- `useFetch(key, fetcher)`: 캐시 키는 요청 경로다 (예: `'/api/processes'`, `` `/api/processes/${id}` ``). 모듈 수준 `Map`에 마지막 응답과 받은 시각을 두고, 캐시가 있으면 처음부터 성공 상태로 그린 뒤 뒤에서 다시 받아 바꾼다
- 정한 것
  - 캐시 유지 시간 5분: 이보다 오래된 응답은 보여 주지 않고 로딩부터 한다 (TanStack Query의 기본 캐시 유지 시간과 같은 값). 보여 줄 때도 항상 다시 받으므로 옛 값이 보이는 시간은 다시 받는 동안뿐이다
  - 다시 받다가 실패하면 옛 응답 대신 오류를 보여 주고 캐시를 지운다. 운영 화면에서 옛 상태를 최신처럼 보여 주지 않기 위해서다
  - 재실행 접수 후 캐시 지우기: 하지 않음. 화면에 들어올 때마다 다시 받으므로 지금은 필요 없다. 로드맵 3번 "재실행 후 이력 갱신"에서 다시 본다
- 아직 하지 않은 것: 필터·검색어를 URL 쿼리(`useSearchParams`)로 옮겨 복귀 후에도 유지하기(동작이 바뀌는 기능 변경), 목록의 링크에 마우스를 올리면 상세를 미리 요청하기
- C# 비유: `MemoryCache`에 둔 값으로 화면을 먼저 그리고, 백그라운드 Task가 새 값을 받아 갱신

### 3. 정적 파일 캐시 헤더 — 적용

- `vercel.json`에 `/assets/(.*)` → `Cache-Control: public, max-age=31536000, immutable`을 추가했다. 내용이 바뀌면 파일 이름의 해시도 바뀌므로 안전하다. 해시가 없는 `index.html`·`mockServiceWorker.js`는 `/assets/` 밖이라 영향이 없다
- 배포 후 확인할 것: DevTools → Network → `assets/index-*.js`의 응답 헤더 `cache-control`이 위 값인지, `/processes/PRC-001`에서 새로고침해도 화면이 뜨는지(rewrites 유지)

### 4. 배포 번들에서 MSW 제거 — 로드맵 4번(실서버 연동)과 함께

- 실 API가 생기면 MSW는 개발 환경에서만 켠다 (`import.meta.env.DEV`나 전용 환경변수로 조건을 걸고 동적 import). 실험 B에서 나눈 청크 크기로 보면 첫 로딩 JS는 698 KB(gzip 246 KB)에서 271 KB(gzip 85 KB)로 준다
- 그 전까지는 "배포 환경에서도 MSW" 결정 때문에 첫 로딩 경로에서 뺄 수 없다

## 지금 하지 않을 것

- `React.memo`·`useMemo` 추가, 목록 가상화: 프로세스 8개·이력 20건이라 렌더링 비용이 측정되지 않는다. 연습하려면 목 데이터를 수천 건으로 늘리는 실험 모드를 만들고, React DevTools Profiler로 먼저 잰 뒤 적용한다
- 화면 단위 코드 분할(`React.lazy`): 앱 코드가 2%라 효과가 없다
- 벤더 청크 분리(`build.rolldownOptions.output.codeSplitting`): 배포가 바뀌어도 라이브러리 파일의 브라우저 캐시를 유지하는 효과뿐이다. 재방문이 많아지면 3번과 함께 검토한다
