- 내가 판단하거나 수정한 것과 그 이유:
  - 단계마다 개념 확인 질문에 답하고, 이해가 확인된 뒤에만 다음 단계로 넘어가기로 함 — 진도를 빠르게 나가면서도 핵심 개념은 확실히 파악하기 위해

  - `fetch`는 4xx·5xx 응답에도 예외를 던지지 않는다 → `res.ok`로 직접 확인 (C# `EnsureSuccessStatusCode`와 비슷)

  - 판별 유니온: 타입은 가능한 모양의 목록이고, 값은 그중 하나다. `status`를 확인하면 그 모양의 필드만 쓸 수 있다
  - `Record<유니온, 값>`은 모든 키를 채워야 컴파일된다. CSS 클래스 이름은 타입 검사 대상이 아니다
  - 목록의 `key`는 행을 구분하는 고유하고 바뀌지 않는 값(`id`)을 쓴다

- AI가 제안한 것:

  - 상세·실행 이력 MSW 핸들러와 명세 형식(`{ code, message }`)의 404 응답
  - 실패 응답 본문에서 서버 메시지를 꺼내 화면까지 전달하는 fetch 함수 구조
  - 화면 표시 컴포넌트 분리(`RunTable`, `ProcessInfo`, `TriggerChip`)와 포맷 함수의 `src/utils` 이동
  - 개발자 요청으로 일부 수정(실행 이력 핸들러 마무리, 상세 화면 빌드 오류 수정)은 AI가 직접 작성
- 내가 판단하거나 수정한 것과 그 이유:
  - 화면 전환 방식으로 React Router를 선택함 — 상세 화면을 URL로 나눠 주소 공유·새로고침·뒤로가기가 되도록 하기 위해 (새 패키지라 설치 이유를 확인한 뒤 승인)
- 새로 배운 개념:
  - 라우트 매칭은 선언 순서가 아니라 경로의 구체성으로 정해진다 (`path="*"`를 맨 위에 둬도 결과가 같다)
  - `<Link>`는 페이지를 새로 받지 않고 URL과 화면만 바꾼다. SPA 딥링크는 서버가 모든 경로에 `index.html`을 줘야 새로고침이 된다
  - 타입 좁히기는 검사한 그 변수에만 적용된다. 같은 함수를 다시 부르면 좁혀지지 않은 새 값이 된다
  - `{ }`는 위치에 따라 코드 블록·객체 만들기·구조 분해 패턴으로 뜻이 달라진다. spread(`...`)는 새 객체를 만들어 복사하므로 원본은 바뀌지 않는다
  - `unknown`은 타입이고 `'error'`는 상태 값이다. 유니온 리터럴 타입은 정의되지 않은 값을 컴파일 단계에서 막아 준다
  - 자동 import가 내부 경로나 같은 이름의 목 함수를 고를 수 있으므로 import 경로를 확인한다
